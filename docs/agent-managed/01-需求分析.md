# Agent 会话管理解耦：需求分析

执行模式：`Developer Mode · Requirements`
状态：方向已确认，代码尚未实施
范围：HarvisBar 中现有 `Chat Agent Managed` / `CodexAgentManaged` 功能域

## 1. 输入边界

- 用户确认将跨 Provider 的 Chat Agent Managed 从 Codex 产品边界中独立出来。
- 本阶段只落盘需求、架构和开发计划，不修改业务源码、运行配置、安装产物或持久化数据。
- 当前工作树存在其他并行改动；后续实施必须先记录 `git status --porcelain`，不得覆盖、清理或顺手修复无关文件。
- Codex、DSH、WorkBuddy 当前能力并不对等；统一展示不代表统一获得写权限。
- 现有 Codex durable queue、审批、handoff、窗口吸附和 `deliveryUnknown` 安全语义必须保持。

## 2. 背景

现有实现处于过渡状态：入口、目录、窗口类型和偏好键仍以 Codex 命名，但数据与管理视图已经跨 Provider。

已确认的现状包括：

- `ManagedChatProvider` 已包含 Codex、DSH、WorkBuddy。
- `refreshManagedChatProviders()` 已聚合三路来源并统一刷新治理状态。
- 管理窗口已经提供 Provider 筛选、跨 Provider 项目归组、Attention、Insight 和 Plan。
- DSH、WorkBuddy 的会话目前主要是只读观察；Codex 承担精确打开、派发、审批、handoff 和工作台能力。
- 通用模型仍泄漏 `supportsCodexDispatch`、`supportsCodexWorkbench`、`CodexThreadTrustProjection` 等 Codex 语义。
- 当前紧凑导航已有三行十二个入口，继续追加一级按钮会增加拥挤和职责重叠。

因此问题不是“是否支持多个 Provider”，而是“代码所有权和依赖方向尚未匹配已经发生的多 Provider 产品事实”。

### 2.1 四个正交概念

| 轴 | 含义 | 当前例子 |
| --- | --- | --- |
| Provider / 会话来源 | 独立的会话命名空间、发现源和动作授权边界 | Codex、DSH、WorkBuddy |
| Account / Authority | Provider 内决定当前权限的账号或 endpoint | 主 Codex `CODEX_HOME`、DSH endpoint authority |
| Agent Identity / Profile / Skill | 在某个 Provider/运行环境中工作的智能体身份与技能 | main、`cxspark`、`cxglm` |
| Harness / Model / Runtime Preset | 智能体如何执行、使用哪个模型及其便捷绑定 | Codex harness、GLM model、某个 CX Agent 关联的 runtime preset |

CX 系列默认属于 Agent/Profile/Skill 或 Runtime Preset，不是新的会话 Provider。只有某对象拥有独立、稳定的会话地址、发现源、authority 和动作传输层时，才重新评审是否加入 Provider Registry。技能存在本身不授予 send、approve、archive 等管理权限。

## 3. 目标

### 3.1 核心目标

建立独立的 `Agent Managed` / `Managed Conversations` 业务域，使：

1. 通用会话身份、能力、信任状态、项目归组和治理规则不依赖 Codex 类型。
2. Core 不直接依赖 `HarvisRuntimeModel`、SwiftUI、AppKit 或具体 Provider 通信协议。
3. Codex、DSH、WorkBuddy 通过显式 Adapter 和动作级 Capability 接入。
4. `HarvisRuntimeModel` 只负责应用组装、生命周期和向 UI 发布 Snapshot，不成为 Core 的输入对象。
5. UI 能统一展示各 Provider，同时严格隐藏或禁用未声明能力。
6. 迁移期间不丢失现有窗口布局、标签、置顶、项目分配、Attention、队列或 handoff 状态。

### 3.2 产品目标

- 用户可从中性入口打开“Agent 会话管理”，默认看到所有 Provider。
- Codex 页面保留兼容快捷入口，并可按 Codex 过滤打开。
- `丙·Agent` 可提供轻量入口，但不复制完整管理器。
- V1 不新增第十三个紧凑一级导航按钮。
- 完整管理器继续运行在 HarvisBar 同一 App / 进程中。

### 3.3 工程目标

- 先在现有 `HarvisBar` target 内形成可验证的目录和协议边界。
- SwiftPM target 拆分作为后置 Go/No-Go 门，而不是第一阶段前置条件。
- 每个阶段具备独立测试、回滚点和兼容策略。
- 未来新增 Provider 时，不需要在通用 Core 中增加 `if provider == ...` 才能安全接入。

## 4. 产品边界

| 模块 | 回答的问题 | 保留职责 | 不承担 |
| --- | --- | --- | --- |
| `乙·Codex` | Codex 本身是否可用、账户和运行状态如何 | `CODEX_HOME`、登录、额度、CLI/Desktop、app-server、Codex 配置与进程 | 跨 Provider 会话治理的所有权 |
| `Agent 会话管理` | 所有 Agent 会话是什么、属于哪个项目、当前可执行哪些会话级动作 | 列表、搜索、筛选、项目归组、Attention、Insight、Plan、能力路由 | Provider 账户管理、伪造通用写能力 |
| `丙·Agent` | 有哪些 Agent、启动器、Mail、Harness 和知识能力 | Agent 启动与能力目录、轻量入口 | 复制完整会话管理器 |
| `1·Work` | 跨系统有哪些工作正在推进、排队或阻塞 | 工作摘要和 Studio 深链接 | 会话级检查器、派发器和治理编辑 |
| `B·DSH` | 哪些 DSH App/Profile 可启动或正在运行 | DSH Runtime Catalog 与 App 启动 | 取代跨 Provider 会话管理 |

## 5. 用户场景

1. 用户从 `Open` 菜单进入 Agent 会话管理，查看 Codex、DSH、WorkBuddy 的统一列表，并按来源、项目和状态筛选。
2. 用户选择 Codex 会话时，可使用派发、审批、handoff、Inspector 和窗口吸附等 Codex 专属能力。
3. 用户选择只读 DSH 或 WorkBuddy 会话时，只看到已声明的状态和安全打开动作；Insight 仅在该会话具备可信输入契约后出现，不存在的派发按钮不会出现。
4. 某个 Provider 刷新失败时，其他 Provider 仍可使用，失败来源有明确且不泄密的错误状态。
5. 用户升级后，原有窗口大小、展开状态、置顶、项目归组和标签保持可用。
6. 开发者接入新 Provider 时，实现发现与能力端口并通过契约测试，无需修改 Codex Adapter 的内部协议。

### 5.1 界面应展示的功能投影

| 区域 | 展示内容 | 可执行动作边界 |
| --- | --- | --- |
| 通用管理区 | Provider、账号/authority 状态、Agent identity、会话状态、项目、Attention、Plan、Insight、freshness 与来源错误 | 搜索、筛选、归组和治理；会话动作仍逐项检查 Capability |
| Codex 详情 | 主账号状态、CX Agent（含 `cxspark` / `cxglm`）身份与技能、turn、quota、Evidence、Inspector、Composer、approval、handoff | 仅在当前会话 decision 与 authority 同时允许时执行；Sidechat 可路由到 parent，transient 默认拒绝 |
| DSH 详情 | Runtime/App/Profile/Host 与会话摘要、Catalog/Host 表面入口、明确的只读或 stale 状态 | 当前仅开放已验证的 surface open；管理服务存在不等于具体 DSH 会话具备 send 或 Insight 输入权 |
| WorkBuddy 详情 | 受管 App、会话摘要、安装/连接与只读状态 | 当前仅开放受管 App 表面；精确打开、输入读取和写动作均保持拒绝，直到有可信契约 |

统一界面负责把各 App 的真实功能“投影过来”，不要求三个 Provider 长得完全一样，也不通过灰色假按钮暗示尚未存在的能力。

## 6. 功能需求

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 独立业务所有权 | 通用源码位于 `AgentManaged/`，不再由 `CodexAgentManaged/` 作为顶层所有者 |
| FR-02 | 精确跨 Provider 身份 | 会话 ID 至少包含 `providerID + scope + sourceID`，无跨来源碰撞 |
| FR-03 | Provider-neutral Core | Core 的公开模型和规则不引用 `HarvisRuntimeModel`、`CodexThread*`、SwiftUI 或 AppKit |
| FR-04 | 动作级 Capability | 能力至少覆盖 observe、openProviderSurface、openExact、readInputs、send、steer、interrupt、approve、archive、fork、handoff |
| FR-05 | Capability 按会话解析 | 同一 Provider 的不同会话可返回不同能力；决策可携带 direct/parent 目标、拒绝原因和 authority revision，UI 不只依赖 Provider 全局布尔值 |
| FR-06 | Provider 端口隔离 | 发现、打开、读取输入、派发、审批、Insight/Planner 使用可分离端口，不建立万能 Provider 协议 |
| FR-07 | 多来源刷新隔离 | 单个 Provider 失败不清空其他来源，不把陈旧数据伪装成新鲜结果 |
| FR-08 | Codex 专属能力留在 Adapter | app-server、账户、额度、queue、approval、handoff、Codex 深链与吸附不进入 Core |
| FR-09 | DSH/WorkBuddy fail-closed | 未声明 send/approve 等能力时，动作不可调用；当前只读约束有契约测试 |
| FR-10 | 中性 UI | 标题、筛选、空态和项目视图不假设 Codex；Provider 专属面板由路由选择 |
| FR-11 | 兼容入口 | 旧 `openCodexChatManager()`、`--open-codex-manager` 可在迁移期委托到新入口 |
| FR-12 | 偏好与身份迁移 | 旧 `harvis.codex.chatManager.*` 和旧 storage key 可双读迁移，用户状态不丢失 |
| FR-13 | 安全投递语义保持 | 持久化先于发送、不确定结果不自动重放、终态不被陈旧更新复活 |
| FR-14 | 中性入口 | `Open` 菜单提供 Agent 会话管理；Codex 和 Agent 页只保留快捷入口 |
| FR-15 | Target 拆分门 | 只有满足文档定义的依赖、契约测试和构建门后才新增 SwiftPM target |

## 7. 非功能需求

### 7.1 安全

- Capability 默认返回 `denied` decision；Provider 未显式证明的动作一律不可用，UI 不得把“没有按钮”当作唯一防线。
- 通用层不得把 Provider 原始 URL、Token、Cookie、环境变量或认证对象写入可展示模型。
- Codex 的审批、queue 和 handoff 状态机在迁移前先由 characterization tests 冻结。
- Provider 错误必须脱敏，不向另一个 Provider 回退执行。

### 7.2 可靠性

- 刷新必须支持取消、generation 校验和来源级错误隔离。
- Provider 移除、endpoint authority 丢失或账号切换时，旧 Snapshot 不得继续授予动作能力。
- 持久化迁移必须幂等，可重复运行且不重复写入业务动作。

### 7.3 可测试性

- Core 规则使用值类型和合成数据测试，不要求启动 AppKit、真实进程或网络服务。
- 每个 Adapter 运行同一套 Provider contract tests，并可追加 Provider 专属测试。
- UI 测试使用注入的 Snapshot/Capabilities，不发起真实模型调用。

### 7.4 可维护性

- 现有约 3400 行的主 View 必须按列表、工具栏、项目矩阵、工作台和 Provider 详情拆分。
- 文件依赖保持单向，避免 Core 通过 extension 偷读全局 RuntimeModel。
- 新 Provider 不要求修改通用状态机；若必须修改，需新增 ADR 解释抽象缺口。

### 7.5 兼容性

- 迁移期保持旧命令行入口、窗口恢复和 UserDefaults 键可读。
- 兼容代码必须有删除条件和最晚清理阶段，避免永久双轨。

## 8. 明确不做

- 本轮规划不修改业务代码。
- V1 不拆第二个 macOS App、XPC service 或独立进程。
- V1 不立即增加一级导航按钮或第四排导航。
- Phase 1 不立即创建 SwiftPM library target。
- 不为了统一界面把 DSH、WorkBuddy 提升为可写 Provider。
- 不把 Codex app-server JSON-RPC、`CODEX_HOME` 或窗口磁吸抽象成所有 Provider 都必须实现的接口。
- 不一次性重命名并删除所有旧 UserDefaults / storage key。
- 不设计外部动态插件 SDK；先完成内置 Provider 的静态注册和契约。
- 不把 CX Skill、Agent Profile、Harness、Model 或 Runtime Preset 仅凭名称注册为会话 Provider。
- 不在重构过程中顺手改变排序、视觉样式、派发策略或治理业务规则。

## 9. 已证伪或暂缓的选项

| 选项 | 结论 | 原因 |
| --- | --- | --- |
| 继续归属 Codex | 已证伪 | 数据和 UI 已跨三个 Provider，命名会继续扩大反向依赖 |
| 立即新增一级导航 | 暂缓 | 当前已有十二个入口，非 Codex Provider 主要只读，页面价值与 Agent/Work/DSH 有重叠 |
| 立即拆独立 App | 已证伪 | 会引入状态同步、权限、窗口生命周期和偏好迁移成本，没有独立进程价值 |
| 立即拆 SwiftPM target | 暂缓 | 当前主 View、RuntimeModel、窗口和持久化依赖仍双向，先拆会扩大访问级别和循环依赖问题 |
| 一个巨大 Provider 协议 | 已证伪 | 会迫使只读 Provider 伪实现派发、审批等能力，违反接口隔离和 fail-closed |
| 只按 Provider 声明能力 | 已证伪 | 同一 Provider 内会话类型、授权和 endpoint authority 可能不同，能力必须细化到会话 |

## 10. 开放决策与默认值

| 决策 | 当前默认 | 重新评审触发条件 |
| --- | --- | --- |
| 用户可见名称 | `Agent 会话管理`，展开态为 `Agent Workbench` | 全局产品命名统一调整 |
| 内部模块名 | `AgentManaged` | Core target 正式拆分时统一命名 |
| 一级导航 | 不新增；使用 `Open` + Agent/Codex 快捷入口 | 至少两个 Provider 具有真实管理动作且紧凑页有独有价值 |
| SwiftPM target | 暂不拆 | Core 零 UI/App 依赖、零 RuntimeModel 反向依赖、至少两个 Adapter 通过契约测试 |
| Provider 注册 | App composition root 静态注册 | 出现外部 Provider SDK 或频繁第三方扩展需求 |

## 11. 总体验收定义

完成本项目必须同时满足：

1. 通用 Core 不依赖 `HarvisRuntimeModel`、SwiftUI、AppKit 或 Codex 具体类型。
2. Codex、DSH、WorkBuddy 均通过统一身份、发现、Capability 和错误隔离契约测试。
3. 不支持的 Provider 动作在 Core、Runtime 和 UI 三层都 fail-closed。
4. 旧用户偏好、标签、项目分配和窗口状态有可验证迁移路径。
5. Codex queue、approval、handoff 和 `deliveryUnknown` 行为无回归。
6. 中性入口、Provider 筛选和专属详情路由通过 UI 与无障碍验收。
7. HarvisBar 全量测试、Release 构建和受控视觉验收通过。
8. SwiftPM target 仅在 Go/No-Go 门通过后创建；未通过不阻塞业务域解耦验收。
