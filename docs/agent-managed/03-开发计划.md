# Agent 会话管理解耦：开发计划

执行模式：`Developer Mode · Plan`
状态：Phase 0、Phase 1 已完成并通过验收；停止于 Phase 1，尚未进入 Phase 2
前置文档：[01-需求分析](./01-需求分析.md)、[02-架构设计](./02-架构设计.md)

## 1. 执行原则

1. 一个 Phase 使用一个新会话，只实现该阶段，不跨阶段顺手重构。
2. 每阶段开始先读取三份文档和当阶段相关源码，再记录 `git status --porcelain`。
3. 当前仓库存在并行改动；实施前必须确认目标文件没有其他写入者，测试使用唯一 scratch path。
4. 每阶段结束必须更新本计划 checkbox、实际测试结果、风险和偏差。
5. 阶段边界是建议提交边界；只暂存当阶段明确文件，不使用 `git add -A`，不擅自发布或安装。
6. 不支持的 Provider 动作始终 fail-closed，不以“后续会实现”为理由临时放开。
7. 文档与源码不符时停止扩大范围，将差异回写“设计偏差”，由用户决定是否修改 ADR。
8. SwiftPM target 不是项目成功的必要条件；业务域边界正确才是必要条件。

## 6. Phase 2：Provider Ports、Registry 与 Adapter

Developer Mode：`Provider Boundary`

### 6.1 目标

把发现、打开、读取输入、派发、审批和 Insight/Planner 分成小端口，由三类 Provider 显式声明和实现。

### 6.2 允许修改

- `AgentManaged/Core` 的端口契约。
- 新增 `AgentManaged/Providers/{Codex,DSH,WorkBuddy}`。
- 现有三类 ManagedChat Adapter 与相应 tests。
- Provider Registry。

### 6.3 任务

- [ ] 定义 `ConversationDiscovering` 与来源级 batch/freshness/error 契约。
- [ ] 分别定义可选的 SurfaceOpening、ExactOpening、InputReading、Dispatching、Steering、Interrupting、Approval、Archiving、Forking、Handoff、Insight、Planning 端口，不能用“能打开 App”冒充“能精确打开会话”。
- [ ] Registry 验证 Provider ID 唯一、发布的 Capability 均有实现端口。
- [ ] Codex Adapter 封装 Home scope、app-server、精确打开、派发、审批和 handoff。
- [ ] DSH Adapter 封装 Catalog/Host endpoint authority、Session 映射和安全打开；写能力保持关闭。
- [ ] WorkBuddy Adapter 封装发现与打开；写能力保持关闭。
- [ ] 不把 CX Agent Profile/Skill、Harness、Model 或 Runtime Preset 注册为会话 Provider，除非它有独立地址、authority 和生命周期契约。
- [ ] 建立共享 Provider contract suite，并为每个 Adapter 运行。

## 7. Phase 3：Application Runtime 与持久化迁移

Developer Mode：`Application Runtime`

### 7.1 目标

用 `AgentManagedCoordinator` 聚合 Provider，通过 Snapshot 驱动应用；`HarvisRuntimeModel` 退回 composition/presentation 边界。

### 7.2 允许修改

- 新增 `AgentManaged/Runtime/`。
- `HarvisRuntimeModel.swift` 与专用 `HarvisRuntimeModel+AgentManaged.swift`。
- Conversation Management / Insight / Governance 的协调代码。
- 通用偏好和 storage key 迁移器及 tests。
- Codex queue/handoff 只允许做接线迁移，不改状态机语义。

### 7.3 任务

- [ ] 新增聚合 Snapshot，包含 per-provider freshness、错误和 generation。
- [ ] 新增 Coordinator，支持并发刷新、取消、scope/authority 变化与旧结果拒绝提交。
- [ ] 新增 CapabilityRouter，每次动作前按当前 generation/authority revision 重验 decision 和端口，并使用 decision 指定的 direct/parent target。
- [ ] `HarvisRuntimeModel` 创建 adapters/coordinator，只发布安全 Snapshot 或兼容投影。
- [ ] 将项目归组、治理刷新和 Insight 输入从 RuntimeModel extension 移入专用 Runtime 用例。
- [ ] 新增 `harvis.agentManaged.*` 偏好命名空间和 schema version。
- [ ] 实现新键优先、旧键双读、校验后迁移；暂不删除旧键。
- [ ] 只为当前已发现、已验证的 Codex conversation 计算 exact legacy alias；禁止拆分任意 `scope::id` 猜测身份。
- [ ] 可由旧格式表达的偏好至少一个兼容周期双写；非 Codex selected conversation 只写新键并记录降级限制。
- [ ] 为迁移幂等、损坏值、安全默认和重复启动编写测试。
- [ ] 保持 Codex durable queue/handoff 的不确定投递语义。

### 7.4 验收

- Core/Coordinator 不持有或接收整个 HarvisRuntimeModel。
- Provider 单点失败、取消和慢请求不会跨 generation 污染 Snapshot。
- authority 丢失后写 Capability 立即撤销。
- 新旧投影在 fixture 上等价；迁移重复运行不会重复业务动作。
- queue/handoff/approval 既有 tests 全绿。

### 7.5 明确不做

- 不改主 UI 和窗口标题。
- 不删除旧 Published 属性；兼容期只委托。
- 不删除旧偏好或业务数据。

## 12. 术语与接入判定

权威参考：[Agent Pools Interface](../agent-pools-interface.md)、[Agent Roster Interface](../agent-roster-interface.md)。

| 概念 | 示例 | 是否天然是 Agent Managed Provider |
| --- | --- | --- |
| 会话 Provider / 来源 | Codex、DSH、WorkBuddy | 是，但仍须实现精确地址和发现契约 |
| Account / Authority | 主 Codex 账号、某 DSH endpoint authority | 否；它决定 Provider 内权限和 Capability |
| Agent Identity / Profile / Skill | Agent Roster identity、`cxspark` / `cxglm` Agent Skill | 否；除非拥有独立会话生命周期与地址 |
| Harness | Codex CLI、Kimi Code、Claude Code | 否；它是执行方式 |
| Model | GLM、Codex model、DeepSeek model | 否；它是推理后端 |
| Runtime Preset | 某个 CX Agent 关联的 harness + model 配置 | 否；它是执行绑定，不是新 Provider |

新增对象只有同时具备稳定 `providerID`、精确 conversation address、独立 authority 和生命周期发现契约时，才进入 Provider Registry。

## 13. 兼容代码删除条件

- 迁移遥测仅使用非敏感本地计数，确认旧键不再是唯一来源。
- 用户窗口、tags/pins/project assignment fixture 可从新键完整恢复。
- 删除兼容层有独立测试和 ADR，不与 Provider 功能开发混合。
