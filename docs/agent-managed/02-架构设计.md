# Agent 会话管理解耦：架构设计

执行模式：`Developer Mode · Architecture`
状态：设计基线 v1，代码尚未实施
前置文档：`01-需求分析.md`

## 1. 设计目标

把已经跨 Codex、DSH、WorkBuddy 的会话管理能力调整为独立业务域，同时保持 HarvisBar 单进程、现有行为和安全语义不变。架构先建立单向依赖，再决定是否机械拆分 SwiftPM target。

设计必须满足：

- Core 只表达会话领域事实和纯规则。
- Runtime 负责用例、聚合、刷新、能力路由和持久化协调。
- Provider Adapter 负责具体发现、传输、打开和动作协议。
- UI 只消费 Snapshot / Presentation，不直接猜测 Provider 能力。
- `HarvisRuntimeModel` 是 composition root 与应用发布边界，不是 Core 服务定位器。
- 未声明能力默认拒绝，不能因加入统一列表而扩大权限。

## 2. 当前依赖问题

当前概念依赖近似如下：

```text
HarvisCodexChatManagerView
    ├─ 读取 HarvisRuntimeModel 的全部 managed chat 状态
    ├─ 混合通用列表、项目治理、Codex 账户和 Codex Workbench
    └─ 通过 provider switch 选择 DSH / WorkBuddy 只读详情

HarvisRuntimeModel
    ├─ 聚合 Codex / DSH / WorkBuddy
    ├─ 保存 UI、服务、窗口和持久化状态
    └─ 直接构造 ManagedChatThread

ManagedChatThread（名义通用）
    ├─ ManagedChatProvider
    ├─ supportsCodexDispatch / supportsCodexWorkbench
    └─ CodexThreadTrustProjection
```

如果把上述代码直接搬进新 target，容易形成：

```text
HarvisBar -> AgentManagedCore -> HarvisBar(HarvisRuntimeModel)
```

SwiftPM 不允许循环 target 依赖；即使仍在同一 target，这种反向依赖也会让 Core 无法独立测试和复用。

### 2.1 为什么 Core 不能依赖 `HarvisRuntimeModel`

`HarvisRuntimeModel` 是 HarvisBar 外层的可变应用对象，聚合了生命周期、窗口、服务、偏好和 UI 发布状态；Core 则应只表达会话身份、能力与状态转换。若 Core 反向读取 RuntimeModel：

1. 依赖方向会从“App 组装 Core”变成“Core 知道 App”，未来拆 target 时必然形成循环。
2. 领域规则会隐式依赖全局可变状态，测试必须启动整套应用，无法用合成值验证。
3. Provider、窗口或偏好变化会渗入 Core API，使新增 DSH、WorkBuddy 或其他 Agent 来源继续修改中央对象。
4. authority/generation 可能在读取期间变化，动作安全边界变得不可审计。

因此不是 RuntimeModel “不能使用 Core”，而是依赖必须单向：RuntimeModel 创建并调用 Coordinator/Core，再发布 Snapshot；Core 只能接收明确值和窄端口。

## 3. 目标分层

```text
界面层
  AgentManagedUI / AgentManagedViewModel
        │ 只读取 presentation，发送用户意图
        ▼
应用层
  AgentManagedCoordinator / CapabilityRouter / PersistenceGateway
        │ 依赖 Core 规则与 Provider ports
        ▼
领域层
  AgentManagedCore
  identity / snapshot / capability / trust / project / state machine
        ▲
        │ 实现分离的 ports
基础设施与 Provider 层
  CodexAdapter     DshAdapter     WorkBuddyAdapter
  app-server       Host API       local CLI / app open

HarvisBar Composition Root
  HarvisRuntimeModel 创建并注入 adapters + coordinator，
  再把稳定 snapshot 暴露给菜单栏和窗口。
```

依赖规则：箭头只能从外层指向内层；Core 不 import 外层。

## 5. Core 模型

### 5.1 Provider 与精确地址

```swift
struct AgentProviderID: RawRepresentable, Hashable, Sendable {
    let rawValue: String
}

struct ManagedConversationAddress: Hashable, Sendable {
    let providerID: AgentProviderID
    let scope: String
    let sourceID: String
}
```

约束：

- `providerID + scope + sourceID` 是完整身份，序列化后仍可无歧义恢复。
- `scope` 由 Provider 定义，但必须稳定、非敏感且不能包含凭据。
- UI 标题、项目路径或模型名不得作为身份。
- 原始 Provider 对象只存在 Adapter 内，不进入 Core 持久化。

### 5.2 标准化会话

```text
ManagedConversation
├── address
├── title / titleSource / hasMeaningfulTitle
├── createdAt / updatedAt
├── tokenUsage（可选；未知使用 nil，不使用 -1 哨兵）
├── lifecycle: running | idle | completed | failed | archived | unknown
├── projectContext（可选、安全投影）
├── lineage（root / parent / subagent / sidechat）
├── agentIdentity（身份/角色/skill IDs；只作身份与展示，不授予动作）
├── activity
├── trust
├── capabilities
└── providerMetadata（受限、可展示键值；不得装入任意对象）
```

`ManagedChatThread` 在兼容期可作为 typealias 或转换器存在，最终由 `ManagedConversation` 取代。

### 5.3 Agent Identity 与 CX 系列

```text
Provider: Codex
Authority/Scope: 主账号对应的 CODEX_HOME
Agent Identity/Profile/Skill: main / cxspark / cxglm / 其他 CX 智能体
Conversation: thread / subagent / sidechat
```

`AgentIdentity` 可包含稳定 ID、显示名、角色、preset/skill IDs 等非敏感元数据。它与 Provider Capability 分离：一个 Agent 拥有某项 Skill，不代表 Harvis 获得对该会话 send、approve、archive 或 handoff 的权限。

`cxspark`、`cxglm` 当前不注册为独立 Provider。只有它们未来具备独立会话命名空间、发现接口、authority 和动作传输层时，才重新评审 Adapter 边界。

### 5.4 Capability

Capability 按具体会话和当前 authority 解析。不能只使用 `Set<Action>`，因为“允许发送”仍可能要求发送到 parent，而不是当前卡：

```text
observe
openProviderSurface
openExact
readInputs
send
steer
interrupt
approve
archive
fork
handoff
inspect
analyzeInsight
plan
```

```text
ConversationCapabilityDecision
├── allowedDirect(authorityRevision)
├── allowedVia(targetAddress, authorityRevision)
└── denied(safeReason)

ConversationCapabilitySnapshot
└── decisions: action -> decision
```

例如 Codex main/persistent subagent 可为 direct send，受管 sidechat 可能只能 `allowedVia(parentAddress)`，transient sidechat 必须拒绝。steer、approve 等动作还需绑定当前 turn / approval authority，不能由一个长期布尔值代表。

规则：

1. 默认全部 denied，只有 Adapter 明确证明时才返回 allowed decision。
2. Capability Snapshot 带 generation / authority revision；账号、endpoint、turn 或授权变化后旧能力失效。
3. UI 是否显示动作、Runtime 是否接受动作、Adapter 是否执行动作必须三层一致。
4. Runtime 执行前重新解析 decision，并严格使用 decision 给出的 direct/parent/explicit target，不能由 UI 自行改写目标。
5. Provider 全局能力只能作为上限，最终能力仍由具体会话解析。
6. `supportsCodexDispatch` 等名称不进入 Core。

`openProviderSurface` 与 `openExact` 必须分开：WorkBuddy 当前只打开受管 App，DSH 当前只保证打开 Runtime/Host 表面；两者不能因此宣称能精确定位某个会话。

### 5.5 Trust 与生命周期

`ConversationTrustState` 取代通用模型中的 `CodexThreadTrustProjection`：

```text
unknown / running / idle / completed / failed / archived
```

Provider Adapter 负责把自身状态映射为通用状态，并保留安全、可展示的 reason。Core 只定义状态含义和允许的转换，不解析 Provider 原始字符串。

## 6. Provider 端口

采用接口隔离，不建立一个要求所有 Provider 实现所有动作的万能协议。

```swift
protocol ConversationDiscovering {
    var providerID: AgentProviderID { get }
    func discover() async throws -> ProviderConversationBatch
}

protocol ConversationSurfaceOpening {
    var providerID: AgentProviderID { get }
    func openProviderSurface() async throws
}

protocol ConversationExactOpening {
    func openExact(_ address: ManagedConversationAddress) async throws
}

protocol ConversationInputReading {
    func readInputs(_ address: ManagedConversationAddress) async throws
        -> ManagedConversationInput
}

protocol ConversationCommandDispatching {
    func send(_ command: ManagedConversationCommand) async throws
        -> ManagedDeliveryReceipt
}

protocol ConversationApprovalResponding { /* provider-specific implementation */ }
protocol ConversationSteering { /* optional */ }
protocol ConversationInterrupting { /* optional */ }
protocol ConversationArchiving { /* optional */ }
protocol ConversationForking { /* optional */ }
protocol ConversationHandoffProviding { /* optional */ }
protocol ConversationInsightProviding { /* optional */ }
protocol ConversationPlanning { /* optional */ }
```

实际签名在 Phase 2 根据 characterization tests 固化；上述接口用于约束职责，不作为提前承诺的最终 API。

## 7. Runtime 设计

### 7.1 Provider 注册

`AgentManagedProviderRegistry` 由 HarvisBar composition root 静态创建：

```text
codex      -> discovery + surface/exact open + input + dispatch + approval + handoff
dsh        -> discovery + surface open；可选管理服务不自动变成会话 Insight Capability
workbuddy  -> discovery + surface open
```

V1 不做动态插件加载。Registry 拒绝重复 Provider ID，并能生成供 UI 使用的非敏感 descriptor。

### 7.2 聚合刷新

```text
idle
  -> refreshing(generation N)
  -> provider batches arrive independently
     -> validate identity/capabilities
     -> merge by exact address
     -> project governance and presentation
  -> ready(snapshot N, per-provider freshness/errors)

scope/authority changes
  -> increment generation
  -> cancel old work
  -> revoke stale capabilities
  -> old result cannot commit
```

单个 Provider 失败：

- 不清空其他 Provider。
- 是否保留该 Provider 的旧只读 Snapshot 由 freshness policy 决定，并明确标记 stale。
- 会授予写权限的 Capability 在 authority 不可确认时立即撤销。
- 错误按来源保存，不把 Provider A 的失败映射为 Provider B 的 fallback。

### 7.3 动作路由

```text
UI intent
  -> address + requested capability
  -> CapabilityRouter revalidates current decision + authority revision
  -> resolve direct / parent / explicit target from decision
  -> resolve matching Provider port
  -> persist intent/state when required
  -> execute Adapter action
  -> commit success / failure / deliveryUnknown
```

任何层缺少 Capability 或地址不匹配都失败关闭。

## 8. `HarvisRuntimeModel` 的位置

迁移后的 `HarvisRuntimeModel`：

- 创建 `AgentManagedCoordinator` 与 Provider Adapter。
- 订阅 Coordinator 的安全 Snapshot，并在兼容期映射为旧 Published 属性。
- 转发明确的用户意图，不再包含项目归组、Capability 和 Provider 路由规则。
- 不被 Core 持有、传入或读取。

目标依赖：

```text
HarvisRuntimeModel -> AgentManagedRuntime -> AgentManagedCore
HarvisRuntimeModel -> Codex/DSH/WorkBuddy Adapter -> AgentManagedCore
AgentManagedCore -X-> HarvisRuntimeModel
```

## 9. UI 架构

### 9.1 通用外壳

`AgentManagedView` 只负责：

- All / Provider / status / project / tag 筛选。
- 会话列表和项目矩阵。
- Attention、Plan、Insight 的通用 Presentation。
- Provider badge、freshness、错误和只读状态。
- 将用户意图发送给专用 ViewModel / Coordinator。

### 9.2 Provider 详情路由

```text
ProviderDetailRouter
├── Codex -> CodexWorkbenchDetail / TurnPanel / Inspector / Evidence
├── DSH -> DshConversationDetail / safe surface open / capability-verified insight
└── WorkBuddy -> WorkBuddyReadOnlyDetail / safe open
```

通用 UI 不通过 `if isCodex` 推断写权限，而读取当前会话的 Capability。

### 9.3 入口策略

- `Open` 菜单新增中性“Agent 会话管理”。
- `乙·Codex` 保留兼容入口，并以 Codex filter 打开。
- `丙·Agent` 可增加一个轻量入口卡，不复制完整列表。
- 旧窗口 title、CLI 参数和方法在兼容期委托到新 WindowController。
- V1 不新增一级导航 section。

## 10. 持久化与兼容契约

### 10.1 键迁移

旧键示例：

```text
harvis.codex.chatManager.layout
harvis.codex.chatManager.showSidechats
harvis.codex.chatManager.selectedThreadID
harvis.codex.chatManager.selectedProjectID
harvis.codex.chatManager.workbenchExpanded
```

新命名空间：

```text
harvis.agentManaged.*
```

迁移规则：

1. 若新键存在，优先读取新键。
2. 若只有旧键，校验后写入对应新键，并记录 schema version。
3. 迁移不删除旧键；可由旧格式表达的偏好至少一个兼容发布周期双写，以保留降级能力。
4. selected conversation 必须把旧 ID 转为完整地址；无法无歧义转换时安全清空选择，不猜测。
5. 窗口 pin/dock/size 的迁移独立于会话业务数据。

### 10.2 Storage key

新 storage key 统一使用完整地址。旧 Codex `scope::id` 键采用显式别名双读：

```text
read new provider::scope::id
  -> absent: 对当前已发现且已验证的 Codex conversation 计算 exact legacy alias
  -> exact alias match 后读取旧值
  -> write new key
```

不得通过拆分任意 `scope::id` 字符串猜测身份，也不得把 DSH/WorkBuddy ID 用旧 Codex 规则解析。无法由旧格式表达的非 Codex selected conversation 只写新键，并记录旧版降级后的明确限制。

### 10.3 投递安全

- durable queue 和 handoff 数据继续由 Codex Adapter 所有。
- 保持“先持久化，再发送”。
- 进程退出、连接断开或响应不确定时进入 `deliveryUnknown`，不得自动重放。
- terminal state 不得被挂起任务的陈旧候选状态覆盖。

## 13. SwiftPM target Go/No-Go 门

业务域解耦完成后，只有同时满足以下条件才创建 `HarvisAgentManagementCore` library target：

- [ ] Core 源码不出现 `HarvisRuntimeModel`。
- [ ] Core 不 import SwiftUI、AppKit、Combine、Network 或 Provider SDK。
- [ ] Core 不引用 `Codex*`、`Dsh*`、`WorkBuddy*` 具体类型。
- [ ] Core 的所有测试无需 `NSApplication`、真实进程、真实网络或用户凭据。
- [ ] 至少 Codex 与一个非 Codex Adapter 通过统一 contract suite；只读 Provider 必须通过拒绝写动作的契约。
- [ ] Runtime 与 UI 只通过 Core public API 依赖它，不为拆 target 暴露整个应用内部状态。
- [ ] `swift test`、Release build、偏好迁移和窗口恢复测试全绿。
- [ ] 依赖审计确认不会形成 `HarvisBar <-> Core` 循环。

通过后，先只移动纯 Core 到 `Sources/HarvisAgentManagementCore/`。Runtime、UI 和 AppKit WindowController 继续留在 HarvisBar；除非出现第二个真实消费端，否则不再拆更多 target。

## 14. 扩展点

- 新 Provider：注册 descriptor + discovery adapter；其他动作端口按真实能力选择实现。
- 新 Capability：先定义安全语义和失败状态，再扩展 Adapter 与 UI；不能只加按钮。
- 新 Insight/Planner：作为可选服务端口，不塞入 discovery 协议。
- 外部插件 Provider：只有静态内置 Provider 边界稳定后再单独设计 SDK、权限和签名策略。
- 一级导航：当两个以上 Provider 具备常用写操作且形成独有紧凑摘要时重新评审。

## 15. ADR 简表

| ADR | 决策 | 原因 |
| --- | --- | --- |
| ADR-01 | Agent 会话管理独立为业务域 | 当前数据、项目治理和 UI 已跨三个 Provider |
| ADR-02 | V1 继续同一 App/进程 | 避免状态同步、权限、窗口和偏好生命周期复杂化 |
| ADR-03 | Core 不依赖 RuntimeModel/UI 框架 | 保持单向依赖、纯测试和未来 target 可拆性 |
| ADR-04 | Capability 按动作、按会话解析 | Provider 能力不对等，授权和 endpoint authority 会动态变化 |
| ADR-05 | 多个小端口代替万能 Provider 协议 | 只读 Provider 不应伪实现派发/审批 |
| ADR-06 | 默认 fail-closed | 统一展示不能扩大执行权限 |
| ADR-07 | 先同 target 分层，后 target Go/No-Go | 避免把语义重构与 Swift 访问级别重写绑在一起 |
| ADR-08 | 不立即新增一级导航 | 当前十二入口已饱和，非 Codex Provider 主要只读 |
| ADR-09 | 旧入口和偏好渐进迁移 | 保证窗口状态、用户组织数据与脚本兼容 |
| ADR-10 | Codex queue/handoff 留在 Adapter | 它们依赖 Codex app-server 和特殊的不确定投递安全语义 |
| ADR-11 | Provider、Authority、Agent/Skill、Harness/Model 四轴分离 | 避免把 cxspark/cxglm 等 CX 智能体或 preset 误注册为会话 Provider |
| ADR-12 | Capability 使用带目标和 authority 的 decision，而非纯布尔/集合 | 保留 sidechat parent routing、turn/approval authority 与安全拒绝原因 |

## 16. 异常处理

| 场景 | 预期行为 |
| --- | --- |
| Provider discovery 失败 | 只标记该来源，其他来源继续可用 |
| authority 丢失 | 立即撤销相关写 Capability，旧异步结果不可恢复它 |
| 地址无法解析 | 拒绝动作并提供非敏感错误，不猜测 Provider |
| 旧偏好迁移失败 | 保留旧值并使用安全默认，不删除原键 |
| Adapter 声称能力但无对应端口 | Registry 启动校验失败，该能力不发布 |
| 动作结果不确定 | 进入 provider-defined unknown 状态，禁止自动重放 |
| 单个 Insight/Planner 失败 | 不影响会话发现与普通打开，单独展示功能错误 |
| 新 Core target 门未通过 | 保持同 target 的清晰分层，不阻塞业务解耦交付 |

## 17. 架构验收清单

- [ ] 所有依赖符合界面层 → 应用层 → Core 的单向规则。
- [ ] Core 可用合成值测试，不初始化 HarvisRuntimeModel 或 AppKit。
- [ ] Provider Adapter 不通过全局单例取得另一个 Provider 的权限。
- [ ] UI 不以 `isCodex` 代替 Capability 判断。
- [ ] 精确地址、Capability generation 和 freshness 可观察、可测试。
- [ ] 旧入口、偏好、storage key 和窗口恢复有迁移测试。
- [ ] Codex 专属 app-server/queue/handoff/attach 未泄漏进 Core。
- [ ] SwiftPM target 拆分是门控的机械迁移，而不是修复架构的手段。
