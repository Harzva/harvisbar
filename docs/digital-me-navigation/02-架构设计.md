# 数字导航第三排：架构设计

状态：Phase 0 数据契约核查后定稿，执行中

## 1. 设计目标

在不改变现有运行权限、不复制 Studio 业务逻辑的前提下，为 HarvisBar 增加第三排 Digital-Me 导航。菜单栏弹窗负责聚合与跳转，Studio 继续负责完整证据、编辑和状态变更。

## 2. 系统关系

```text
Codex / DSH / Agent / Harvis runtime state
                    │
                    ▼
       DigitalMeNavigationProjection
        ├─ work summary
        ├─ review summary
        ├─ memory summary
        └─ persona summary
                    │
                    ▼
HarvisBar compact read-only sections (318 × 620)
        │                 │
        │ select section  └─ safe deep link
        ▼                                   ▼
1 Work / 2 Review / 3 Memory / 4 Persona   Harvis Studio full views
```

## 3. 模块职责

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `HarvisBarSection` | 定义 12 个导航 section 及可见前缀、标题 | 业务状态分类 |
| `navigationRows` | 定义三行顺序，确保每个 section 恰好出现一次 | 页面内容 |
| `DigitalMeNavigationProjection` | 把已有 Runtime/Studio 状态投影为四个只读摘要 | 网络请求、副作用、审批决定 |
| `DigitalMeNavigationStore` | 按需读取 approvals、memory candidates 和 persona 三个只读接口并保留来源错误 | 两秒全局轮询、业务写入 |
| `HarvisDigitalMePopoverSections` | 渲染紧凑卡片、空态、错误态和 Studio 入口 | 复制完整 Studio UI |
| Studio | 展示完整证据，处理审批、Memory、Persona 编辑 | 菜单栏布局 |

## 5. 导航模型

建议保留语义清晰的三个分组，并增加统一入口：

```swift
static let primarySections: [HarvisBarSection] = [/* 甲乙丙丁 */]
static let utilitySections: [HarvisBarSection] = [/* A-D */]
static let digitalMeSections: [HarvisBarSection] = [/* 1-4 */]

static let navigationRows: [[HarvisBarSection]] = [
    primarySections,
    utilitySections,
    digitalMeSections,
]
```

Picker 遍历 `navigationRows`，而不是继续手写第三个 row 调用。这样测试可以验证：

- 每行恰好四个入口；
- 三行扁平化后等于 `allCases`；
- 没有定义后忘记渲染的 section；
- 没有重复入口。

`selectedSection` 继续是本地 UI 状态，默认仍为 `.overview`。新增 section 不需要数据迁移。

## 6. 只读投影模型

建议使用不可变、可单元测试的摘要，而不是在 SwiftUI `body` 中分散计算：

```text
DigitalMeNavigationSnapshot
├── work
│   ├── activeCount
│   ├── queuedCount
│   ├── blockedCount
│   └── primaryItem
├── review
│   ├── approvalCount
│   ├── memoryCandidateCount
│   ├── personalityCandidateCount
│   └── totalAttentionCount
├── memory
│   ├── vaultCount
│   ├── snapshotExists
│   ├── lastSnapshotAt
│   ├── candidateSignalCount
│   └── knowledgeSourceCount
└── persona
    ├── activePersonaCount
    ├── runningTwinCount
    ├── activeNames
    ├── registryVersion
    └── reviewQueueVersion
```

字段允许为 `nil`，以区分“Runtime 尚未提供”与真实的 `0`。V1 优先复用当前模型已有数据；缺失数据展示“尚不可用”，不要用伪造计数填满页面。

## 7. 数据与状态规则

### 7.1 Work

- `running/active` 归入活动工作。
- `queued/waiting` 归入等待队列。
- `blocked/failed/deliveryUnknown` 在 Work 中只显示摘要，同时引导到 Review 或完整详情。
- 选择 Work 页面本身不触发新的任务、进程或 handoff。

### 7.2 Review

- 聚合 Approval、Memory Candidate 和 Personality Candidate。
- Review 的注意计数是三类待处理项之和，但页面内必须分开展示类别，不能让用户误解为同一种审批。
- 普通 Approval 必须排除 `target.kind == memory_candidate`，避免和 Memory Candidate 重复计数。
- Memory Candidate 以 `/memory-candidates` 的真实未决候选为主；V1 不把同一候选在 `/approvals` 的镜像再次相加。
- 红色提示只代表“需要注意”，不代表已失败。
- 弹窗不提供 Approve / Reject；只打开完整 Review Center。

### 7.3 Memory

- 当前 HTTP API 没有 Memory Provider 的可信 accepted 数量；禁止显示初始化后长期为 `0` 的 `memory_items` 作为真实 accepted 计数。
- Candidate 提供“候选项在 Review 中处理”的说明。
- 默认只展示 Vault、快照时间、候选信号和知识源数量，不展示原始正文。

### 7.4 Persona

- 展示 active Persona Card / running Twin 的数量、非敏感名称与注册表版本。
- API 没有 selected/current 字段，不能把数组第一项称为当前 Persona / Twin。
- API 没有 evaluation state，V1 不伪造测试结论。
- 主动作打开 Persona Studio，次动作可打开 Copy-Me Builder。
- 保存、创建、测试等写操作由 Studio 承担。

## 8. 深链接约定

复用现有 Studio URL 构造逻辑，追加受控的 view 参数：

| 紧凑页 | 主目标 |
| --- | --- |
| Work | `/studio/?view=work` |
| Review | `/studio/?view=review` |
| Memory | `/studio/?view=memory` |
| Persona | `/studio/?view=studio` |
| Persona 次入口 | `/studio/?view=copy` |

URL 必须由现有安全构造器生成；不得把令牌、私有 Workspace 根目录或其他敏感值拼进可复制、可记录的 URL。

## 9. 交互与布局

- 第三排复用现有四等分按钮、3pt 间距、选中填充和边框。
- `1/2/3/4` 是可见层级编号，不是快捷键声明。
- V1 只给 Review 增加必要的红色状态点；其他徽标在有明确价值时再加，避免 12 个按钮同时闪烁。
- 状态点用 overlay，不参与标题宽度计算。
- 四个页面采用统一结构：标题摘要、2–4 个关键指标、最多三条列表、完整工作台按钮。
- 页面切换应回到内容起点；若现有单一 ScrollView 无法可靠做到，使用 section ID 驱动的 ScrollViewReader 或将 picker 与内容滚动区分离。

## 10. 安全与隐私边界

- 菜单栏页面只读；不扩大 HarvisBar 的执行权限。
- 不显示 token、cookie、环境变量、原始会话、原始记忆、未脱敏路径或日志。
- Review 的决定必须在能展示证据、范围和影响的完整界面中完成。
- Runtime 断开时显示断开状态，不回退到过期数据并伪装成实时状态。
- approvals、memory candidates、persona 只在弹窗出现或进入对应页面时按需刷新并缓存，不加入两秒一次的全局轮询。
- 深链接失败时给出可恢复提示，不自动启动或重启服务。

## 11. 架构决策记录

### ADR-01：选择 Work / Review / Memory / Persona

原因：它们构成 Digital-Me 的稳定闭环，并与 Studio 已有对象一致；比按任务状态或按应用窗口划分更少重复。

### ADR-02：第三排是内容导航，不是动作条

原因：它位于已有 section picker 内，保持一致的选中态与紧凑摘要能降低认知切换。启动 Desktop / Studio 等动作继续留在现有 action strip。

### ADR-03：弹窗只读、完整操作深链接

原因：318px 宽度无法可靠承载审批证据、记忆正文和 Persona 编辑；高影响操作必须保留完整上下文。

### ADR-04：数字前缀不等于键盘快捷键

原因：Tools 页面存在文本输入和密码输入，裸数字会劫持正常输入。未来如确有需求，单独设计 `⌘1–⌘4`。

### ADR-05：导航行必须完整覆盖 allCases

原因：Swift 的穷举 switch 能发现漏写内容映射，却不能发现“定义了 section 但没有渲染”。统一行模型与集合测试补上这一缺口。

## 12. 异常处理

| 场景 | UI 行为 |
| --- | --- |
| 数据加载中 | 显示稳定 skeleton 或“正在读取”，不显示假 `0` |
| Runtime 断开 | 显示断开与“打开 Studio/检查服务”入口，不自动重启 |
| 无工作/无审核项 | 明确的正常空状态，不使用警告色 |
| 单个来源失败 | 展示可用部分并标记来源不完整 |
| Studio URL 不可用 | 禁用打开按钮并解释配置缺失 |
| 深链接打开失败 | 显示可恢复错误，不改变当前 section |
