# 数字导航第三排：需求分析

状态：用户已确认，执行中  
范围：HarvisBar 菜单栏弹窗  
推荐命名：`1·Work / 2·Review / 3·Memory / 4·Persona`

## 1. 背景与目标

HarvisBar 当前使用两排、每排四个入口：

| 层级 | 现有入口 | 语义 |
| --- | --- | --- |
| 第一排 | `甲·总览 / 乙·Codex / 丙·Agent / 丁·Harvis` | 核心驾驶舱与运行域 |
| 第二排 | `A·Network / B·DSH / C·Ports / D·Tools` | 基础设施与本地工具 |

第三排不应再重复某个运行时或工具，而应补上 Digital-Me 自身的工作闭环。推荐：

```text
1·Work  →  2·Review  →  3·Memory  →  4·Persona
执行工作     人工决策       审核后沉淀      身份与行为呈现
```

这一组与 Studio 已有的 Work、Review Center、Memory、Persona Studio / Copy-Me Builder 对齐，不需要创造一套新的产品分类。

## 2. 推荐入口

| 按钮 | 紧凑页内容 | 完整工作台目标 | 状态提示 |
| --- | --- | --- | --- |
| `1·Work` | 当前工作、运行中任务、优先队列、handoff 与阻塞摘要 | Studio Work | 有活动时可显示绿色状态点 |
| `2·Review` | Approval、Memory Candidate、Personality Review 的待处理汇总 | Studio Review Center | 有待处理项时显示红色状态点或小计数 |
| `3·Memory` | Vault、最近快照、候选信号和知识源数量；候选项只提示去 Review | Studio Memory | 默认不显示常驻徽标 |
| `4·Persona` | Active Persona / Running Twin 数量、注册表版本和编辑器入口 | Persona Studio；次入口为 Copy-Me Builder | 默认不显示常驻徽标 |

### 2.1 Work 与现有页面的边界

- `甲·总览` 继续回答“系统现在是否健康”。
- `乙·Codex` 继续负责 Codex 账户、会话、进程和配置。
- `丙·Agent` 继续负责 Agent Mail、知识源、启动器等 Agent 能力。
- `1·Work` 回答“跨 Codex、DSH 和 Agent，现在有哪些工作正在推进或等待处理”。

### 2.2 Memory 与 Knowledge 的边界

- `丙·Agent` 中的 Knowledge 是外部知识源、索引和图谱。
- `3·Memory` 是经审核后属于 Digital-Me 的个人记忆、快照和 Vault。
- 未审核的 Memory Candidate 属于 `2·Review`，不能伪装成已接纳记忆。

### 2.3 Persona 的边界

- `4·Persona` 不是 Agent 启动器，也不是模型选择器。
- 它展示当前身份卡、行为规则、Copy-Me 绑定和测试状态。
- 编辑与创建动作进入完整 Persona Studio / Copy-Me Builder 完成。

## 3. 用户场景

1. 用户打开菜单栏弹窗，点击 `1·Work`，快速确认当前工作和阻塞状态，再进入完整 Work 页面查看证据。
2. `2·Review` 出现红点时，用户先查看待审批类别和数量，再进入 Review Center 作出有证据的决定。
3. 用户点击 `3·Memory` 查看 Vault、最后一次快照、候选信号和知识源数量，不在小弹窗中浏览原始记忆正文。
4. 用户点击 `4·Persona` 查看 Active Persona / Running Twin 的数量和非敏感名称，并选择打开 Persona Editor、Builder 或 Test Room。

## 4. 功能需求

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 增加第三排四个入口 | 顺序固定为 Work、Review、Memory、Persona，前缀固定为 `1/2/3/4` |
| FR-02 | 保留现有导航 | 原有两排的顺序、标题、默认总览和进入页面时的刷新行为不变 |
| FR-03 | 入口是内容导航 | 点击后在弹窗内展示对应紧凑页，选中态与现有按钮一致 |
| FR-04 | 提供完整工作台入口 | 每个紧凑页至少有一个明确的“在 Studio 中打开”动作 |
| FR-05 | Review 有高优先级提示 | 存在待处理项时可见红色状态提示；无待处理项时不制造警报感 |
| FR-06 | 紧凑页只读 | 不在弹窗内批准、拒绝、接纳记忆、修改 Persona 或启动高影响动作 |
| FR-07 | 错误与空状态明确 | Runtime 不可用、无数据、加载中和正常空队列必须可区分 |
| FR-08 | 数字仅作视觉编号 | V1 不绑定裸 `1–4` 键盘快捷键 |
| FR-09 | 页面数据安全 | 不展示原始聊天正文、原始记忆正文、令牌、私有绝对路径或未脱敏日志 |

## 5. 非功能需求

- 固定 `318 × 620` 弹窗中三排必须完整可见，无横向溢出。
- 每个按钮标题保持单行；英文标题长度不得比现有布局承载能力更差。
- 新页面不得在“切换到该页”时启动进程、改变审批状态或写入持久化数据。
- VoiceOver 使用完整语义名称，例如“Work，Digital-Me 工作队列”；不能暗示数字键已注册为快捷键。
- Glass 与 Graphite 主题下，选中态、未选中态和 Review 警示均需有足够区分度。
- 切换长页面时应回到新页面可理解的起点，不能让用户误以为页面为空。

## 6. 明确不做

- 不把第三排做成 `Desktop / Studio / Panel / Presence`；这些入口已在 Open 菜单和底部快捷动作中存在。
- 不做 `Projects / Tasks / Inbox / History` 的另一套任务管理树；它会与总览、Codex Manager、Agent Mail 和 Logs 重复。
- 不把 Memory Candidate 自动写入 Memory。
- 不显示“已接纳记忆数”；当前 HTTP 契约没有 Memory Provider 的可信 accepted 计数。
- 不把数组第一项称为“当前 Persona / Twin”；当前 API 允许多个 active/running 项且没有 selected 字段。
- 不在 318px 宽的紧凑 Review 页完成批准/拒绝；完整证据和影响必须在 Review Center 查看。
- V1 不持久化最后选中的第三排页面。
- V1 不绑定裸数字键；若以后需要快捷键，单独评审 `⌘1–⌘4` 及输入框焦点行为。

## 7. 命名结论

推荐保留英文短标题，因为现有第二排已采用英文技术名词，且 Studio 的正式对象也是英文命名：

```text
1·Work | 2·Review | 3·Memory | 4·Persona
```

中文可作为 tooltip / accessibility 文案：

```text
工作 | 审核 | 记忆 | 人格
```

若未来产品整体切换为中文导航，可统一替换为 `1·工作 / 2·审核 / 3·记忆 / 4·人格`，但不建议只把第三排做成中英文混杂的例外。

## 8. 需求验收结论

规划满足三个条件：

1. 新增的是 Digital-Me 层，不重复已有运行域和基础设施层。
2. 四个入口能形成 `Work → Review → Memory → Persona` 的可解释闭环。
3. 小弹窗只做状态摘要与导航，高影响决策仍留在完整工作台。
