# Harvis 版本管理：需求分析

## 1. 目标

把 Harvis 自身纳入 HarvisBar 的本地版本管理界面，与已有 DSH Runtime Catalog 和项目 Git 元数据体验同级。操作者必须能从一个界面回答：

1. 当前 HarvisBar App 是什么版本？
2. 当前安装包由哪个源码 commit 构建？
3. 当前稳定 helper 是否与 receipt 绑定的 runtime 一致？
4. 当前绑定的 Harvis 源码 worktree 在哪里，属于什么 branch/HEAD，是否 dirty？
5. 源码 HEAD 与已安装 commit 是对齐、领先、落后、分叉还是无法证明？
6. Harvis 是否已配置 Git remote/upstream，若未配置必须如实显示，不伪造 GitHub 关联。

## 2. 必须分离的用户身份与执行产物

| 身份 | 权威数据 | 界面用途 |
| --- | --- | --- |
| Source | 用户明确选择的 Harvis Git worktree | branch、HEAD、dirty、upstream、ahead/behind、worktrees |
| Installed App | App bundle `Info.plist` | HarvisBar 应用版本、bundle identity |
| Provenance payload | App Resources 内受 receipt 绑定的不可编辑 payload | 已安装 source commit/tree、provenance SHA |
| Stable helper | 用户 home 下固定的 `.harvis/bin/harvis`，并与 HTTP/Tick 两个 LaunchAgent `ProgramArguments[0]` 交叉校验 | helper SHA/size 与 receipt runtime record 对齐 |
| Runtime API | 当前 `/health` 响应 | API 协议版本与在线/离线状态 |

Source 路径不得复用运行时 `pluginRoot`：正式 App 必须继续优先使用 receipt/provenance 覆盖的 bundle payload，不得因为版本界面而恢复从开发卷执行代码。同时必须把 bundle 中的 `scripts/harvis` command wrapper、bundle payload 中 receipt 绑定的 `bin/harvis` runtime 与已安装 stable helper 当作三个独立角色；v0.1 对 wrapper 只显示固定 role/relative-path context，不读取或哈希其内容，对 bundled runtime 只显示已严格验证的 receipt record，只有 stable helper 做实际文件 size/SHA 校验。`serviceManagerPath` 可能指向 wrapper，不是 stable-helper 权威。

## 3. 用户场景

### S1：快速确认当前版本

操作者从“丁 · Harvis”进入版本管理，看到 App、API、helper 和已安装 source commit，无需打开 Terminal。

### S2：绑定或更换源码 worktree

首次使用时显示“未绑定源码”。用户通过目录选择器选择通过 Harvis markers 校验的 Git worktree。路径只保存在本机 UserDefaults，不写入仓库、receipt、日志或 HTTP DTO。

### S3：判断已安装与源码关系

界面将 receipt source commit 与选定 worktree HEAD 进行本地 ancestry 校验，给出 `exact/sourceAhead/installedAhead/diverged/missingCommit/unknown` 中一种稳定状态。

### S4：检查 Git/GitHub 关联

界面展示 remote 名称、upstream 和基于本地 tracking ref 的 ahead/behind，并显示 `observedAt`与“本地快照，可能陈旧”；由于禁止 fetch，不得将它表述为 GitHub 实时状态。没有 remote 时明确显示“未配置远程仓库”。只有已存在且通过严格语法验证的 GitHub HTTPS remote 才允许“打开 GitHub”；不自动创建、修改或访问远程。

### S5：故障局部降级

receipt 缺失、helper 不可读、Git 超时、source 卷离线或 API 离线都只降级对应卡片，不得让 HarvisBar 全局 Attention 或主界面卡死。尤其`/task-progress`的HTTP400、permission/I/O或malformed失败必须独立于health/bar/version/source：保留最后成功task snapshot，只显示局部错误与专用重试，不写全局`lastError`。

## 4. 功能需求

| ID | 需求 | 验收 |
| --- | --- | --- |
| HVM-FR-001 | 在“丁 · Harvis”页面提供“版本与源码”入口 | 不增加第 13 个导航区，不改变全局动作基数 |
| HVM-FR-002 | 独立可缩放窗口 | 最小 860×560，标准 1060×700，使用原生 sidebar/detail |
| HVM-FR-003 | 显示 App/API/helper/provenance/source 五种用户身份 | 各自有标签；Helper detail 明确 wrapper=context-only、bundled runtime=receipt evidence、stable helper=file-verified，不混同三者 |
| HVM-FR-004 | 选择并持久化 source root | 只接受 Git worktree + Harvis markers，不接受 bundle payload |
| HVM-FR-005 | 只读 Git 状态 | 包含 branch/HEAD/dirty/upstream/ahead/behind/remotes/worktree 明细 |
| HVM-FR-006 | 读取并严格校验 bundle receipt | 拒绝 symlink、超限、unknown schema、非法 SHA/commit |
| HVM-FR-007 | 校验 stable helper | 显示 helper 路径、存在性和 SHA match/mismatch/unavailable |
| HVM-FR-008 | 已安装/source 对齐 | 只从本地 commit graph 得出，无证据时为 unknown |
| HVM-FR-009 | 安全的本地操作 | 支持刷新、复制、Finder 显示、重选 source |
| HVM-FR-010 | 冷启动测试入口 | `--open-harvis-version-manager` 可直接打开窗口 |

## 5. 非功能需求

- 任何 Git/receipt/helper 检查不在主线程上做无界 I/O。
- 一次刷新共享单调 deadline，Git 默认不超过 5 秒；receipt 上限 1 MiB，helper 上限 128 MiB，Git 每流 1 MiB/每次刷新累计 4 MiB。
- 错误信息面向操作者，不直接显示 raw stderr、remote URL 中的 credential、token 或未过滤的私密路径。
- 界面支持 VoiceOver/AX，刷新、复制、Finder、选择 source 都有稳定 identifier。
- 版本Catalog的启动/刷新/选择不新增API或外网请求：它只消费`HarvisRuntimeModel`已有的本地snapshot，不主动发API请求；不执行Git fetch，并覆盖/预检仓库配置使只读Git查询不得借配置执行外部程序。Phase3的Harvis Popover task-progress修复是独立前置修复，唯一新增请求是fixed no-proxy loopback `GET /task-progress`；禁止redirect、系统proxy、其他endpoint或任何外网连接。

## 6. 明确不做

- 不执行 `fetch/pull/push/clone`。
- shipped UI 与 Phase 1/2 不执行 `checkout/switch/reset/clean/stash/commit/tag`。Phase 3 只在用户明确授权下，于当前专用 local branch 对已验收的产品源码/测试做必要的本地提交，再从该 immutable commit 构建候选版。不 checkout/switch/create branch，不创建 remote，不 push/tag/publish；`docs/02` §9 的 source-checkpoint/transaction 设计已取消，不是本 Goal 的实现或验收门禁。
- 不创建 GitHub remote，不调用 GitHub 写 API，不改变 RepoAtlas 映射。
- shipped 版本管理 UI 不从 source root 执行 Harvis runtime，不覆盖安装 App 或 helper，不暴露更新/回滚按钮。`docs/03` Phase 3 是一次经用户批准的本地开发候选版部署：只复用现有 provenance/packager/bundle verifier、同父目录备份替换与 Rust `service-manager install`，失败时恢复旧 App/helper/plist/service。该流程仅用于本 Goal 验收，不属于产品自动行为，也不证明 ad-hoc 候选版的跨版本 FDA/TCC 身份连续性。
- 不将本机 source root 写入公开仓库、日志、receipt 或 API。
- 不在本功能中修改 DSH Runtime Catalog 的启动/更新逻辑。

## 7. 开放问题与默认决策

| 问题 | v0.1 决策 |
| --- | --- |
| 是否自动发现个人路径？ | 否。production 仅使用已存在的 UserDefaults authority 或用户明确选择；无 key 时保持 unbound，不读取 cwd/环境。闭合 source fixture 只存在于编译隔离的 UI-test build |
| 是否需要 Rust 新 endpoint？ | v0.1 不需要，先用纯 Swift 本地 inspector；不将 source path 放入 HTTP |
| 是否自动更新/回滚？ | 否；shipped UI 不提供。Phase 3 的一次性本地开发部署只使用用户已批准的现有构建/安装/恢复流程，不实现已取消的 transaction/source-checkpoint/Oracle 草案，不扩张 v0.1 功能面 |
| 是否现在发布到 GitHub？ | 否，远程发布继续冻结 |

## 8. GitHub 开源项目调研与复用决策

本轮只读取官方仓库与许可证，不 clone、不增加依赖、不复制源码，也不创建或修改 Harvis remote。可复用的是交互分层、状态命名和安全合同；任何以后真正引入的第三方代码仍需单独完成版本锁定、许可证归档、供应链与二进制体积评审。

| 项目 | 许可证/用途 | v0.1 决策 |
| --- | --- | --- |
| [GitHub Desktop](https://github.com/desktop/desktop) | MIT；Git 仓库状态与 action hierarchy | 只借鉴“当前仓库事实先于动作”的信息层级；不复制 Electron/React 实现 |
| [XcodesApp](https://github.com/XcodesOrg/XcodesApp) | MIT；原生 macOS/SwiftUI 版本列表 | 只借鉴 sidebar/detail、installed/current 状态可视化；不引入其下载、切换或特权 helper |
| [Sparkle](https://github.com/sparkle-project/Sparkle) | Sparkle license；签名校验与原子更新框架 | v0.1 明确延后：当前无 appcast、远程发布冻结，且 shipped UI 不提供更新 |
| [libgit2](https://github.com/libgit2/libgit2) / [SwiftGit2](https://github.com/SwiftGit2/SwiftGit2) | GPLv2 + linking exception / MIT；进程外 Git API 与 Swift value model | 评估后不在 v0.1 引入新 native dependency；保留为以后 stronger openat/fd-bound repository transport 候选 |
| [swift-subprocess](https://github.com/swiftlang/swift-subprocess) | Apache-2.0；Swift structured subprocess | 借鉴 process lifecycle、cancellation/reap 合同；v0.1 继续扩展既有 bounded runner，避免重复执行层 |

结论：v0.1 的 UI 采用原生 macOS sidebar/detail，并把 Installed App、stable helper、source worktree 与 local tracking snapshot 分层；底层继续使用本工程已有 Swift/POSIX seam。`code copied: no`，`dependency added: no`，`remote mutation: no`。
